`0x000000d1` (`DRIVER_IRQL_NOT_LESS_OR_EQUAL`) — не самостоятельная «ошибка Windows». Драйвер режима ядра обратился к страничной или недействительной памяти при слишком высоком IRQL, и Windows остановила работу, чтобы не повредить данные. Так работает защита, а не поломка. Microsoft оценивает, что примерно три четверти ошибок со стоп-кодами вызваны сбойными драйверами.

Ищите не универсальное «исправление 0xD1», а имя модуля: возьмите четыре параметра из Просмотра событий, откройте дамп в WinDbg и выполните команды из инструкции ниже. Затем обновите названный драйвер или откатите его, если он менялся недавно; когда модуль не определён, можно проверить систему через Driver Verifier с осторожностью. Всплеск 0xD1 в 2026 году Microsoft не подтверждала: в release health и на страницах поддержки такой записи нет, есть только единичный вопрос в Microsoft Q&A от 7 ноября.

## Четыре числа в скобках показывают, куда смотреть

В параметрах стоп-кода каждое число описывает отдельную часть сбоя. Первое — адрес памяти, к которой обратились; второе — текущий уровень IRQL; третье — вид операции: `0` означает чтение, `1` — запись, `2` или `8` — выполнение. Четвёртое число — адрес кода, который обратился к памяти. Четыре поля имеют смысл только вместе.

По четвёртому адресу отладчик показывает ближайшую функцию. Для этого выполните команду, подставив адрес из параметра 4:

```text
ln <адрес>
```

Это ориентир для разбора, а не всегда готовое имя устройства: сопоставьте функцию с именем модуля из дампа. Windows также печатает имя определённого драйвера на синем экране и сохраняет его в `KiBugCheckDriver`.

В вопросе от 7 ноября 2026 года параметры приведены сокращённо: `0x000000d1 (0xfffff800f5c75698, 0x2, 0x0, 0xfffff8055faafbee)`. Здесь `0x2` — IRQL `DISPATCH_LEVEL`, а `0x0` — чтение; само наличие этих чисел ещё не называет конкретный драйвер. Неизвестно, какой модуль вызвал сбой у автора вопроса: дамп выложен ссылкой, его содержимое не разбиралось.

Не смешивайте этот код с соседними стоп-кодами. `0x7E` означает необработанное исключение системного потока, а первый параметр там — код исключения, не адрес памяти. `0xC2` относится к некорректному запросу к пулу и требует другого набора проверок. Поэтому начинайте с кода и его параметров, а не с общего описания синего экрана. Сначала параметры, потом действия.

## Имя драйвера ищут в журнале и дампе

Сначала получите параметры падения из системного журнала. Откройте **Просмотр событий → Журналы Windows → Система**, найдите событие BugCheck и посмотрите его свойства: там указаны все четыре параметра. Если экран ещё показывает имя драйвера, запишите и его.

Проверьте, сохранился ли дамп. Дамп хранит имя модуля. В командной строке выполните:

```cmd
dir C:\Windows\Minidump
dir C:\Windows\MEMORY.DMP
```

Минидамп может помочь связать стоп-код с конкретным модулем. Подход к чтению дампа и поиску ошибки в стеке показан на примере [синего экрана 0x154 и минидампа](/articles/bsod-0x154-minidump-disk/).

Для разбора установите WinDbg:

```cmd
winget install Microsoft.WinDbg
```

Откройте файл `.dmp` в WinDbg и выполните:

```text
!analyze -v
dx KiBugCheckDriver
```

В выводе анализа проверьте `WRITE_ADDRESS`, `CURRENT_IRQL`, `MODULE_NAME`, `IMAGE_NAME` и `BUCKET_ID`. В официальном примере Microsoft для 0xD1 указаны адрес `00000004`, IRQL `2` и модуль `USBPORT.SYS`. Это пример разбора, а не утверждение, что у каждого сбоя виноват USB-драйвер. В вашем дампе будет другое имя. Сопоставляйте поля вместе: адрес указывает, к какой памяти обратился код, IRQL показывает уровень операции, а имя модуля, функция и список драйверов помогают связать запись из дампа с устройством и проверить его текущие версию и дату.

Если нужно сопоставить адрес из четвёртого параметра с функцией, выполните команду в WinDbg, подставив адрес из своего события:

```text
ln <адрес>
```

Проверьте, совпадает ли найденный модуль с устройством, чей драйвер менялся перед первым падением, и если совпадение есть, сравните дату установки драйвера с датой первого сбоя в журнале, потому что так видно, совпало обновление с началом падений или даты разошлись и причина в другом. Список установленных пакетов драйверов можно получить так:

```cmd
pnputil /enum-drivers
```

Сведения о подписанных драйверах и версиях покажет команда PowerShell:

```powershell
Get-CimInstance Win32_PnPSignedDriver | Select-Object DeviceName, DriverVersion, DriverDate
```

Отчёт отладчика может указать `ntkrnlmp.exe`, и это не значит, что виновато ядро Windows: Microsoft в таком случае советует разбирать поток дальше. Если имя драйвера не установлено, не делайте вывод по одной этой строке: переходите к проверке Driver Verifier.

## Обновите найденный драйвер, а Verifier включайте осторожно

Если в дампе назван драйвер устройства, загрузите его актуальную версию с сайта производителя. Когда падения начались после недавнего обновления, откройте **Диспетчер устройств → устройство → Свойства → Драйвер → Откатить**. После действия проверьте дату и версию драйвера в том же разделе. Дата и версия должны измениться. Если Windows ставит прежнюю версию обратно, порядок отката разобран на примере [видеокарты](/articles/kak-otkatit-drayver-videokarty-esli-windows-stavit-obratno/).

Если модуль не назван, Driver Verifier может помочь получить новый дамп с дополнительными сведениями, но не обещает автоматически «показать виновника». Microsoft предупреждает, что проверка способна уронить компьютер, требует прав администратора и предназначена для тестовых машин. Сначала сохраните важные файлы. Запустите средство:

```cmd
verifier
```

В окне выберите **Создать стандартные параметры** (англ. Create standard settings), затем перезагрузите компьютер. После следующего падения изучите новый дамп: ожидаемый стоп-код — `0xC4` (`DRIVER_VERIFIER_DETECTED_VIOLATION`), а имя всё равно нужно читать в дампе. Чаще всего новое падение приходит именно с этим кодом, поэтому ждать прежний 0xD1 бессмысленно, а снимать проверку нужно сразу после того, как новый дамп прочитан и модуль назван. Когда проверка закончена, отключите её и перезагрузитесь:

```cmd
verifier /reset
```

Если Windows запустилась после одного падения, не включайте проверку автоматически: Microsoft указывает, что внезапная перезагрузка нередко не требует дополнительных действий. Если 0xD1 повторяется, тогда переходите к диагностике по шагам.

Если дальнейший шаг не сработал, выберите подходящий сценарий:

- **Если дампа нет** → возьмите четыре параметра из события BugCheck и запишите имя модуля с синего экрана, если оно там указано.
- **Если отчёт отладчика показывает `ntkrnlmp.exe`** → не считайте ядро установленным виновником; при повторяющихся падениях используйте Driver Verifier с учётом риска.
- **Если после Verifier появился код `0xC4`** → разберите новый дамп и снимите проверку командой из блока выше.
- **Если Windows не загружается** → войдите в **Безопасный режим** и выполняйте дальнейшие проверки оттуда.
- **Если сбои начались после установки программы или антивируса** → выполните чистую загрузку через `msconfig`: на вкладке **Службы** включите **Не отображать службы Microsoft** и нажмите **Отключить все**, затем проверяйте отключённые службы половинами, а после проверки верните обычную загрузку через **Обычная загрузка** → **Включить все**.
- **Если падение происходит после выключения, а не после перезагрузки** → проверьте, включён ли быстрый запуск: **Параметры → Система → Питание и спящий режим → Дополнительные параметры питания → Действие кнопок питания**.

## Сначала DISM, затем SFC, а память проверьте отдельно

Если нужно проверить целостность системных файлов, соблюдайте порядок из инструкции Microsoft: сначала DISM, затем SFC. DISM подготавливает файлы, которые SFC использует для восстановления. Если запустить SFC первым, ему может не хватить файлов для восстановления. Запустите команды по очереди в терминале с правами администратора:

```cmd
DISM.exe /Online /Cleanup-Image /RestoreHealth
sfc /scannow
```

Оцените результат обеих проверок: дождитесь завершения DISM, затем прочитайте сообщение SFC.

Проверьте и оперативную память встроенным средством Windows:

```cmd
mdsched.exe
```

Согласитесь на перезагрузку и после проверки прочитайте её результат. Замена драйвера не гарантирует, что падения прекратятся: причиной 0xD1 может быть и неисправная планка памяти. Если сбои продолжаются, а проверка памяти не выявила ошибок, дальше проверяют оборудование у его производителя.
