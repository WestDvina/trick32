После чистой установки Windows разработчик редко сразу открывает проект и начинает работать.

Сначала приходится привести систему в порядок. Включить расширения файлов и скрытые элементы. Настроить Проводник. Поставить Terminal, VS Code, Git, PowerToys, WSL. Отключить рекомендации и прочие подсказки, которые полезны обычному пользователю, но только мешают рабочему компьютеру.

Microsoft решила сделать эту подготовительную работу заранее.

4 сентября компания представила **Project Zenith** — готовую конфигурацию Windows 11 для разработчиков. Это не отдельная редакция Windows и не новый ISO-образ. В основе остаётся обычная Windows 11, но система получает набор программ и настроек, рассчитанных именно на разработку.

Идея выглядит простой. Но за ней просматривается довольно серьёзное изменение подхода Microsoft к Windows.

## Zenith не меняет Windows — он меняет её стартовую точку

Project Zenith нельзя установить вместо Windows 11 Home или Pro. Microsoft поставляет его как часть конфигурации определённого класса устройств.

Поэтому правильнее воспринимать Zenith как заранее подготовленное рабочее место.

На обычном компьютере после установки Windows разработчик сам решает, что ему нужно. Microsoft в Zenith делает типовой выбор за него: закрепляет Windows Terminal и Visual Studio Code на панели задач, устанавливает GitHub Copilot, PowerToys, WinAppCLI и Windows Dev Skills.

Это экономит не вычислительные ресурсы, а время.

Если компьютер нужен для разработки, зачем тратить первый час после установки на действия, которые почти наверняка всё равно придётся выполнить?

Именно поэтому самая интересная часть Zenith для меня — даже не список программ.

Это настройки Windows.

## Проводник наконец настроен так, как привык разработчик

В обычной Windows скрытые расширения файлов рассчитаны на человека, которому не нужно думать о структуре имени файла.

Разработчику такой режим часто мешает.

Zenith сразу показывает расширения имён файлов и скрытые элементы. В заголовке окна отображается полный путь, включена панель сведений, а поддержка длинных путей настроена заранее. Недавние файлы и папки и часть подсказок синхронизации, наоборот, отключены.

Это кажется мелочью ровно до того момента, когда Windows создаёт файл `script.py.txt`, а пользователь продолжает думать, что перед ним обычный Python-скрипт.

Для разработчика Проводник — не просто место, куда складывают документы. Через него проходят исходники, конфигурационные файлы, библиотеки, сборки и каталоги проектов. Поэтому такие настройки влияют на ежедневную работу гораздо сильнее, чем очередная кнопка в меню Windows.

Microsoft просто выставила их заранее — тот же набор, который обычно включают вручную: от [расширений имён файлов до уведомлений поставщиков синхронизации](/articles/7-nastroek-windows-11-posle-ustanovki/) в Проводнике.

## Меньше потребительских подсказок

Zenith также убирает часть элементов, которые Microsoft обычно показывает пользователю Windows.

В меню «Пуск» отключаются рекомендации и советы. Система не должна постоянно подталкивать разработчика к дополнительным действиям, связанным с учётной записью и синхронизацией — в обычной Windows 11 такой промпт с резервным копированием OneDrive теперь хотя бы можно [навсегда отклонить одной кнопкой](/articles/windows-11-onedrive-otkaz-ot-rezervnogo-kopirovaniya/).

Это не означает, что Microsoft превратила Windows в минималистичную оболочку.

Она просто сместила приоритеты.

На домашнем компьютере рекомендации могут быть частью интерфейса. На рабочей машине разработчика человек обычно знает, что ему нужно открыть, и не просит Windows подбирать ему следующий шаг.

Такой подход давно используется в специализированных рабочих окружениях. Теперь Microsoft начинает переносить его непосредственно в Windows.

## Windows Terminal, VS Code и PowerToys становятся частью стартового набора

После установки обычной Windows разработчик собирает инструменты самостоятельно.

В Zenith этот этап фактически пропускается.

Windows Terminal нужен для командной строки и PowerShell — в отдельной экспериментальной ветке он уже получил [ИИ-агентов для разбора ошибок прямо в командной строке](/articles/intelligent-terminal-windows-ai/). Visual Studio Code закрывает основной сценарий редактирования кода. PowerToys добавляет инструменты, которых нет в базовой системе, от [переключения между окнами одного приложения](/articles/powertoys-101-window-hopper/) до локальной обработки текста. GitHub Copilot отвечает за ИИ-помощь при разработке. WinAppCLI и Windows Dev Skills расширяют набор именно Windows-инструментов.

Здесь есть важный нюанс.

Я бы не называл такой набор «Windows без мусора».

Это Windows без **чужого** мусора.

Если компьютер принадлежит разработчику, установленный VS Code — полезный инструмент. Если тот же компьютер используется только для бухгалтерии, VS Code превращается в ещё одну программу, которую потом придётся удалять.

Поэтому Zenith хорош не как универсальная Windows, а как пример того, почему универсальная стартовая конфигурация не всегда имеет смысл.

## WSL становится частью рабочего окружения

Разработка давно вышла за пределы одной операционной системы.

Можно писать код в Windows, собирать его в Linux, запускать тесты в контейнере и использовать инструменты, которые изначально создавались под Linux.

WSL позволяет работать с Linux внутри Windows без отдельной виртуальной машины в привычном понимании. В Zenith Microsoft делает эту связку ещё заметнее и добавляет поддержку сценариев с Linux-контейнерами.

Для разработчика это важнее очередной предустановленной программы.

Windows постепенно становится оболочкой, внутри которой можно держать сразу несколько рабочих сред.

Раньше для контейнеров многие пользователи ставили отдельный Docker Desktop. Теперь Microsoft продвигает сценарий, где Linux-контейнеры работают непосредственно через WSL — та же связка PowerShell + Bash + WSL, на которой построен [Intelligent Terminal](/articles/intelligent-terminal-windows-ai/).

Это не означает, что Docker Desktop больше не нужен. Это означает другое: сама Windows получает всё больше компонентов, которые раньше приходилось добавлять отдельно.

## А теперь начинается история про локальный ИИ

Project Zenith Microsoft привязывает к новому классу оборудования.

Для developer-class устройств компания указывает минимум 64 ГБ объединённой памяти и пропускную способность памяти от 250 ГБ/с. Первые системы построены на AMD Ryzen AI Halo.

Для VS Code такие характеристики не нужны.

Они нужны для другой части концепции — локального запуска ИИ.

Microsoft говорит о возможности запускать на таких компьютерах модели с 30 млрд параметров и более без оплаты облачных токенов.

И здесь Project Zenith становится интереснее обычного «Developer PC».

64 ГБ памяти нужны не потому, что разработчику вдруг понадобилось хранить в оперативной памяти огромный проект. Основная причина — возможность держать крупные модели и связанные с ними данные непосредственно на компьютере.

Получается гибридная схема.

Тяжёлую задачу можно отправить в облако. Рутинную — оставить локальной.

Для агентных систем это особенно интересно. Если агент постоянно читает файлы проекта, выполняет команды, проверяет результат и повторяет небольшие операции, часть такой работы можно выполнять непосредственно на компьютере.

Не каждая операция должна превращаться в сетевой запрос с оплатой за токены.

## 64 ГБ — не требование для «Windows разработчика»

Здесь легко неправильно понять идею Microsoft.

Если у вас компьютер с 16 ГБ памяти, это не означает, что Windows 11 внезапно стала непригодной для разработки.

Требования Project Zenith относятся к определённому классу устройств. Microsoft связывает их с высокой пропускной способностью памяти и локальной работой крупных ИИ-моделей.

Для обычной разработки требования намного скромнее.

VS Code, Git, PowerShell, Python, Node.js и WSL не требуют 64 ГБ памяти только ради самого факта запуска.

Поэтому Zenith разумно разделить на две части.

**Программную можно повторить почти на любом достаточно мощном ПК.**

**Аппаратную — только покупкой соответствующей машины.**

И это важное различие, если вы посмотрели на характеристики Zenith и решили, что теперь для Python нужен компьютер с 64 ГБ памяти.

Не нужен.

## Microsoft уже позволяет собрать большую часть Zenith самостоятельно

Для этого даже не обязательно вручную менять десятки параметров.

Microsoft развивает **Windows Developer Config** — открытый проект, который автоматизирует подготовку Windows к разработке. Он устанавливает нужные инструменты и настраивает рабочую среду, включая WSL с Ubuntu. Проект использует конфигурацию WinGet и опубликован на GitHub.

Получается интересная ситуация.

Project Zenith доступен только вместе с определённым классом устройств.

Но сама идея конфигурации Windows для разработчика уже выходит за пределы этих компьютеров.

Если хочется собрать рабочее окружение вручную, достаточно установить базовые компоненты:

```powershell
winget install --id Microsoft.VisualStudioCode --exact
winget install --id Microsoft.WindowsTerminal --exact
winget install --id Microsoft.PowerToys --exact
winget install --id GitHub.Copilot --exact
winget install --id Microsoft.WinAppCli --exact
```

Затем включить WSL:

```powershell
wsl --install
```

И обновить его:

```powershell
wsl --update
```

Проводник можно настроить отдельно: включить **Расширения имён файлов** и **Скрытые элементы**, вывести полный путь и панель сведений, убрать недавно использовавшиеся файлы и включить длинные пути.

Для последнего используется параметр:

```text
HKLM\SYSTEM\CurrentControlSet\Control\FileSystem
LongPathsEnabled = 1
```

После изменения системного параметра лучше перезагрузить компьютер.

Это не создаст на старом ПК полноценный Project Zenith. Но большая часть программной среды будет той же.

## Зачем Microsoft вообще понадобилось делать отдельный профиль

Вот здесь, на мой взгляд, и находится главный смысл проекта.

Windows слишком долго пыталась начинать с одной и той же конфигурации для всех.

Но компьютер разработчика отличается от домашнего ноутбука не только процессором и объёмом памяти.

Разработчику нужны терминал, Git, WSL, редактор кода, инструменты сборки и другая структура Проводника. Ему не нужны некоторые подсказки, рассчитанные на обычного пользователя.

Игровому ПК нужен другой набор.

Рабочему офисному компьютеру — третий.

Поэтому идея разных стартовых конфигураций выглядит логичнее попытки сделать одну Windows одинаково подходящей всем.

Microsoft уже двигается в эту сторону. Project Zenith — один из первых заметных примеров такого подхода.

## Но есть один парадокс

Zenith позиционируется как среда без лишних отвлечений.

При этом Microsoft добавляет в неё GitHub Copilot и делает сильную ставку на ИИ-агентов.

Получается довольно забавная ситуация: компания убирает часть подсказок Windows и одновременно добавляет инструменты, которые будут помогать разработчику писать код.

Разница только в том, кто теперь отвлекает пользователя.

В случае обычных рекомендаций Windows решает за вас, что показать.

В случае Copilot решение принимает сам разработчик — нужен ему ИИ или нет.

Для меня второй вариант выглядит разумнее.

## Что в Project Zenith действительно стоит забрать себе

Покупать специальный компьютер ради нескольких галочек в Проводнике я бы не стал.

А вот сам принцип настройки стоит повторить.

Если вы работаете с кодом, включите расширения файлов и скрытые элементы. Уберите ненужные рекомендации. Поставьте Terminal, VS Code, Git и WSL. Настройте длинные пути.

Это займёт некоторое время один раз.

После этого Windows перестанет каждый раз начинать разговор с вами как с человеком, который впервые включил компьютер.

А если вы регулярно переустанавливаете Windows, лучше автоматизировать процесс через Windows Developer Config или собственную конфигурацию WinGet.

Вот здесь Zenith действительно даёт полезную идею: **не настраивать компьютер заново вручную после каждой установки системы**.

## Моё мнение

Project Zenith не революционизирует Windows.

Большинство его программ можно поставить самостоятельно. Большинство настроек давно доступны в обычной Windows. WSL существует много лет.

Но Microsoft впервые собрала всё это в одну понятную концепцию: разработчику нужен собственный профиль Windows.

И это мне нравится больше, чем очередная новая функция меню «Пуск».

Пока Zenith привязан к новому классу устройств и мощному железу. Но программная часть уже доступна гораздо шире.

А дальше всё будет зависеть от того, насколько Microsoft распространит такие профили.

Если появятся действительно разные конфигурации Windows — для разработки, игр, работы и обычного домашнего использования — пользователю наконец не придётся каждый раз после установки системы объяснять Windows, кто он и зачем купил компьютер.

Именно это, а не VS Code на панели задач, я считаю главным смыслом Project Zenith.
