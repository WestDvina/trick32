**0x80070422** блокирует Центр обновления Windows, а вместе с ним может перестать загружать приложения и Microsoft Store. Сам код не говорит, какая именно служба отключена. Покажу, как найти её и восстановить работу без попыток переустановить Windows наугад.

У ошибки есть точное системное значение: **1058, `ERROR_SERVICE_DISABLED`** — Windows не может запустить отключённую службу. Поэтому повторная проверка обновлений не поможет, пока служба остаётся выключенной. И начинать стоит не с очистки кэша, а с поиска конкретной блокировки.

## Код указывает на службу, а не на загрузку

Неприятная деталь: 0x80070422 не называет виновника. Это может быть одна из служб, нужных для обновлений и установки приложений; в выводе диагностики важно найти тип запуска **Disabled**. А Microsoft Store тоже зависит от доступности конечных точек Центра обновления Windows для установки и обновления приложений, поэтому неисправность проявляется сразу в двух местах.

Не смешивайте эту ошибку с **0x80070005**. Вторая означает отказ в доступе, а не отключённую службу. Если после восстановления служб останется 0x80070005, повторно менять типы запуска бессмысленно: нужно отдельно проверять доступ и политики.

Откройте **Терминал** или **PowerShell от имени администратора**. Сначала запросите состояние основных служб; в списке ищите `Disabled` в колонке `StartType`:

> `Get-Service -Name wuauserv,bits,cryptsvc,trustedinstaller,dosvc,usosvc,installservice | Select-Object Name,Status,StartType`

Для Центра обновления Windows и BITS уточните конфигурацию. В выводе `sc qc` значение `START_TYPE : 4 DISABLED` подтверждает отключённый тип запуска:

> `sc qc wuauserv`
>
> `sc qc bits`

Проверьте и политики, которые могут ограничивать доступ к обновлениям, Store или восстановлению системы. Запросите ветви целиком, включая вложенные параметры:

> `reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate" /s`
>
> `reg query "HKLM\SOFTWARE\Policies\Microsoft\WindowsStore" /s`
>
> `reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\SystemRestore" /s`

Если раздел не найден, соответствующей ветви политики нет. Если найдёте значения `SetDisableUXWUAccess`, `RemoveWindowsStore` или `DisableSR`, удаляйте только конкретное значение, а не весь ключ: рядом могут находиться другие настройки.

## Верните службу, а затем проверьте Store

Тип запуска можно вернуть через `sc.exe config`; команды выполняются в консоли администратора. Для `start=` пробел перед значением обязателен. Эти настройки взяты из справки Microsoft для фиксированных устройств Windows IoT и здесь служат ориентиром для восстановления отключённых служб, а не рекомендацией отключать обновления на обычном компьютере:

> `sc.exe config wuauserv start= demand`
>
> `sc.exe config bits start= demand`
>
> `sc.exe config cryptsvc start= auto`
>
> `sc.exe config dosvc start= auto`
>
> `sc.exe config usosvc start= demand`
>
> `sc.exe config trustedinstaller start= demand`
>
> `sc.exe config installservice start= demand`

Удалите только те параметры политик, которые обнаружили при проверке. Если Windows сообщает, что значение не найдено, пропустите его — значит, этой блокировки нет:

> `reg delete "HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate" /v SetDisableUXWUAccess /f`
>
> `reg delete "HKLM\SOFTWARE\Policies\Microsoft\WindowsStore" /v RemoveWindowsStore /f`
>
> `reg delete "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\SystemRestore" /v DisableSR /f`

Снова выполните `Get-Service` и `sc qc`: вместо `Disabled` должен отображаться ручной или автоматический запуск. Если службы больше не отключены, но обновление всё равно не проходит, следующим шагом можно сбросить кэш обновлений. Этот этап не заменяет проверку служб: он нужен уже после снятия блокировки.

Для сброса остановите **BITS**, **Центр обновления Windows** и **криптографическую службу**, удалите кэш `SoftwareDistribution`, переименуйте `catroot2`, а затем запустите службы снова. Сохранённая папка `catroot2.bak` остаётся на диске; если она уже существует после прошлой попытки, сначала переименуйте её:

> `net stop bits`
>
> `net stop wuauserv`
>
> `net stop cryptsvc`
>
> `rd /s /q %systemroot%\SoftwareDistribution`
>
> `ren %Systemroot%\System32\catroot2 catroot2.bak`
>
> `net start cryptsvc`
>
> `net start bits`
>
> `net start wuauserv`

После этого проверьте системный образ командой **DISM /Online /Cleanup-Image /RestoreHealth**, затем защищённые файлы командой **sfc /scannow**. Обе запускаются с правами администратора. Если Store всё ещё не открывается, проверьте наличие пакета: `Get-AppxPackage *Microsoft.WindowsStore*`. Перерегистрировать приложение нужно в PowerShell без повышения прав, чтобы оно зарегистрировалось для вашей учётной записи:

> `Add-AppxPackage -RegisterByFamilyName -MainPackage Microsoft.WindowsStore_8wekyb3d8bbwe`

Если пакет есть, но приложение не запускается, сбросьте его настройки командой `Get-AppxPackage *Microsoft.WindowsStore* | Reset-AppxPackage`. Полностью удалять Store не стоит: такой способ Microsoft не поддерживает. Подробный разбор проверок и команд есть в [материале об ошибке 0x80070422](https://trick32.ru/articles/oshibka-0x80070422-microsoft-store-i-tsentr-obnovleniya-windows-ne-rabotayut/).

## Если ошибка возвращается

- **Если `sc qc` снова показывает `DISABLED`** — повторно проверьте политики и выясните, что возвращает настройку. Не запускайте сброс кэша снова: он не меняет тип запуска службы.
- **Если после исправления служб появляется 0x80070005** — остановитесь с изменением типов запуска и отдельно проверьте доступ и политики: это другой код.
- **Если DISM не может найти источник восстановления** — укажите доступный источник файлов Windows; без него команда не восстановит образ.
- **Если пакета Store нет или перерегистрация не помогла** — ремонт на месте с установочного носителя может сохранить файлы и приложения. Это не то же самое, что чистая установка, которая удаляет приложения и настройки, а при выборе удаления всего — также личные файлы.

Если службы снова отключаются или отсутствуют, не считайте команды гарантией ремонта. На сборке с вырезанными компонентами их может оказаться недостаточно; переход к установочному носителю — запасной путь, а не обещание, что ошибка исчезнет.
